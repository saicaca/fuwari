用了一段时间 Anthropic 的终端编程工具 [Claude Code](https://claude.com/claude-code) 之后，我发现它有两套很清晰的操作方式：平时写代码、改 bug 这类开放性任务，直接用自然语言提需求就行；但涉及到会话管理、配置切换、代码审查或者项目初始化这类需要明确控制的动作，敲 `/` 开头的斜杠命令会顺手得多。

下面这份速查表是我按日常使用场景整理出来的。因为 Claude Code 更新很快，命令列表也会跟着版本变动，实际有哪些命令可用，记得以你手头客户端里 `/help` 的输出为准。

---

## 1. 会话管理

跑长任务或者频繁切换需求时，这几个命令用来管对话的生命周期最顺手。

| 命令 | 功能 | 示例 / 说明 |
|------|------|-------------|
| `/clear` | 清空当前会话上下文 | 开始全新对话，不影响项目文件和设置。适合切换话题或上下文过长时使用 |
| `/compact` | 压缩会话上下文 | 将对话历史总结为摘要以释放 token 空间。压缩前确保重要内容已落地到文件中 |
| `/rename` | 重命名当前会话标题 | `/rename "修复登录页面布局问题"` |
| `/resume` | 恢复之前的会话 | 继续之前的对话 |
| `/export` | 导出当前会话记录 | 支持多种格式，用于存档、分享或审计 |
| `/prompt` | 显示当前系统提示词 | 查看 CLAUDE.md 注入的项目上下文、记忆、环境信息等 |

## 2. 配置与偏好

想调整终端外观、切换模型或者改权限策略，直接走这组配置命令，不用自己到处翻配置文件。

| 命令 | 功能 | 示例 / 说明 |
|------|------|-------------|
| `/config` | 打开设置界面 | 修改主题、模型、权限策略、hooks 等。等价于编辑 `~/.claude/settings.json` 和 `.claude/settings.json` |
| `/theme` | 切换终端颜色主题 | 暗色 / 亮色 / 系统跟随 |
| `/statusline` | 配置状态栏显示项 | 选择显示模型名、分支、token 用量等信息 |
| `/model` | 切换 AI 模型 | 可用模型取决于订阅计划和最新模型列表 |
| `/fast` | 切换 Fast 模式 | 使用 Opus 模型并加速输出，适合需要快速响应的场景 |

---

## 3. 项目初始化与记忆

刚接手一个新仓库，或者想让 Claude Code 记住某些项目约定，用这三个命令就够了。

| 命令 | 功能 | 示例 / 说明 |
|------|------|-------------|
| `/init` | 生成项目的 CLAUDE.md | 分析项目结构，自动生成包含技术栈、目录结构、常用命令的文档。建议每个项目根目录运行一次 |
| `/memory` | 管理持久记忆 | `/memory 记住：这个项目使用 Biome 格式化代码`。记忆存储在 `.claude/projects/<path>/memory/` |
| `/recall` | 检索相关记忆 | `/recall 代码格式化工具`。Claude Code 启动时自动加载 `MEMORY.md` 索引 |

---

## 4. 代码审查与质量

改完代码提 PR 之前，我通常会顺手跑一遍下面这几个审查命令，提前把明显的问题和冗余代码清掉。

| 命令 | 功能 | 示例 / 说明 |
|------|------|-------------|
| `/review` | 审查当前 Pull Request | `/review --effort high` 指定审查强度；覆盖正确性、安全性、性能、可维护性 |
| `/security-review` | 安全漏洞专项审查 | 覆盖 OWASP Top 10：注入、认证绕过、敏感信息泄露、不安全反序列化等 |
| `/simplify` | 审查并自动简化代码 | 识别可简化、复用、提效的代码模式并自动修复，侧重质量而非 bug |
| `/code-review` | 分级代码审查 | `/code-review --effort low`（仅高置信度）/ `max`（全面）/ `--comment`（发布到 PR） |

## 5. 开发与调试

不只是静态看代码，如果你希望它把项目实际跑起来验证改动效果，可以用这一组命令。

| 命令 | 功能 | 示例 / 说明 |
|------|------|-------------|
| `/run` | 启动并驱动项目应用 | `/run "测试登录功能是否正常"`。自动检测项目类型并选择运行方式 |
| `/verify` | 验证变更实际效果 | `/verify "检查导航栏响应式布局是否修复"`。运行应用并观察行为来确认 |

---

## 6. 任务与后台管理

当手里同时挂着好几个子任务或者后台 Shell 进程时，靠这几个命令查看进度和兜底清理。

| 命令 | 功能 | 示例 / 说明 |
|------|------|-------------|
| `/tasks` | 查看任务列表 | 显示每个任务的状态（pending / in_progress / completed）和依赖关系 |
| `/bashes` | 列出后台 Shell 任务 | 查看所有运行中的后台任务及其状态 |
| `/terminate` | 终止后台任务 | `/terminate <task-id>` |

---

## 7. 自动化与工作流

需要定时轮询某个状态，或者把多个 Agent 串起来跑复杂编排时，可以看看这两个进阶命令。

| 命令 | 功能 | 示例 / 说明 |
|------|------|-------------|
| `/loop` | 按固定间隔循环执行命令 | `/loop 5m /run "检查 Vercel 最新部署状态"`（每 5 分钟）；默认间隔 10 分钟 |
| `/workflows` | 查看和管理多 Agent 编排工作流 | 支持 `parallel()`、`pipeline()`、`phase()` 等编排原语，用 JS 编写脚本 |

---

## 8. 扩展与集成

如果当前工作流需要接数据库、联动 IDE，或者同时跨多个目录改代码，这几个集成入口很关键。

| 命令 | 功能 | 示例 / 说明 |
|------|------|-------------|
| `/mcp` | 管理 MCP 服务器连接 | `/mcp add <server-name>` 添加外部工具/数据源（数据库、API 等） |
| `/ide` | 管理 IDE 集成 | 与 VS Code、JetBrains 等协作，在 IDE 中打开文件、定位到指定行 |
| `/add-dir` | 添加额外工作区目录 | `/add-dir /path/to/another-project`，允许操作多个目录下的文件 |

## 9. 技能类命令（Skills）

除了基础命令，Claude Code 还提供了一批偏专业化场景的 Skills 模块，用来扩展能力边界：

| 命令 | 功能 |
|------|------|
| `/deep-research` | 多源深度调研：自动搜索、交叉验证并生成带引用的报告 |
| `/claude-api` | Claude API / Anthropic SDK 参考：模型 ID、定价、参数、token 计算等 |
| `/update-config` | 通过 settings.json 配置 hooks、权限、环境变量等自动化行为 |
| `/keybindings-help` | 自定义键盘快捷键 |
| `/fewer-permission-prompts` | 分析操作历史，生成权限白名单以减少重复授权弹窗 |
| `/run` | 启动并驱动项目应用以观察变更效果 |
| `/verify` | 验证代码变更是否达到预期效果 |
| `/code-review` | 对当前 diff 进行分级审查 |
| `/simplify` | 审查变更代码的质量优化点并自动修复 |
| `/review` | 审查 Pull Request |
| `/security-review` | 安全审查 |
| `/init` | 初始化项目 CLAUDE.md |
| `/loop` | 定时循环执行任务 |

> Skills 列表会随版本更新持续扩展。使用 `/help` 可查看当前可用的完整 Skills 列表。

## 12. 几个顺手的实战习惯

光背命令表没太大意思，下面分享几个我自己平时用得比较顺手的组合和避坑经验。

### 12.1 把命令串起来用

很多命令串联起来效率会高不少：比如改完代码先跑 `/review` 查问题，紧接着用 `/simplify` 顺手清理和重构；开新项目时则习惯先 `/init` 生成底子，再用 `/config` 按项目微调配置。

### 12.2 行为跑偏时，先用 `/prompt` 看上下文

如果你发现 Claude Code 的回复和预期不太对劲，别急着反复追问，先敲一个 `/prompt` 看看它此刻实际「看到」了哪些上下文——包括 `CLAUDE.md`、持久记忆和系统提示词，很多时候问题一眼就能看出来。

### 12.3 什么时候该执行 `/compact`

不要等上下文爆掉才想起来压缩。遇到下面这几种情况，我就建议主动跑一次 `/compact`（记得先把重要结论落盘到文件里）：

- 上下文 token 使用率超过 80%
- 对话里已经做完好几个彼此独立的任务
- 明显感觉响应速度慢下来了

### 12.4 分清项目级和用户级配置

用 `/config` 改配置时，一定要留意你当前改的是全局还是单个项目，两者的文件路径和生效范围不同：

| 级别 | 路径 | 作用范围 |
|------|------|----------|
| 用户级 | `~/.claude/settings.json` | 适用于所有项目的全局设置 |
| 项目级 | `.claude/settings.json` | 仅对当前项目生效，覆盖用户级设置 |

### 12.5 维护 Memory 的几点原则

持久记忆如果什么都往里塞，久了反而会干扰判断。我自己的习惯是守住这几条边界：

- 只记项目特有的约定和非标准做法
- 记录个人偏好（比如回复语言、代码格式化风格）
- 别把那些看一眼代码或 `git` 历史就能推出来的信息塞进去
- 隔一段时间用 `/recall` 翻一翻，确认旧记忆还没过时

## 使用原则

最后说个自己的使用原则：能用自然语言一句话说清楚的事，就直接聊，没必要为了用命令而用命令；真正需要把配置固化下来、管理长会话或者编排多步任务时，再祭出斜杠命令。如果发现某个命令找不到，或者实际表现跟文里写的不一样，先敲一下 `/help` 和 `/status` 核对当前客户端版本和可用能力。
